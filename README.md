## Хэсэг E: Дүгнэлт

Энэ 60 минутын exploratory testing session-ээр нийт 10 тестийн оролдлого хийснээс 4 нь PASS, 6 нь FAIL үр дүнтэй байв. PASS үр дүнтэй тестүүдэд хүчинтэй мэдээллээр ном нэмэх (T01), ном хайх (T07), хүчинтэй мэдээлэлтэй API хүсэлт боловсруулах (T08), ном устгах (T09) үйлдлүүд багтсан. FAIL үр дүнтэй тестүүдээр хоосон гарчигтай ном UI-аар нэмэгдэх (BUG-01), хоосон зохиогчтой ном нэмэгдэх (BUG-02), зөвшөөрөгдсөн хязгаараас гадуурх 999 болон 2101 онтой ном нэмэгдэх (BUG-03, BUG-04), ижил нэр, зохиогчтой ном давхар нэмэгдэх (BUG-05), мөн API хоосон гарчигтай хүсэлтийг хүлээн авч шинэ бүртгэл үүсгэх (BUG-06) согогууд илэрсэн. Session эхлэхэд хүснэгтэд 3 ном байхад нийт номын тоолуур 4 гэж харагдсан бөгөөд устгах тестийн өмнө болон дараа ч тоолуур хүснэгтийн бодит мөрийн тооноос нэгээр илүү байв. Энэ ажиглалтыг BUG-07 гэсэн тусдаа согог болгон бүртгэх шаардлагатай. Couch Potato аялал нь хоосон болон буруу оролтын боловсруулалтыг шалгахад, Supermodel аялал нь хэрэглэгчийн интерфэйсээр ном нэмэх болон давхардсан номын зан төлөвийг шалгахад, Saboteur аялал нь API-ийн буруу оролтын боловсруулалтыг шалгахад тусалсан. Fed-Ex аяллаар ном устгах үйлдлийн дараа хүснэгтийн мөр болон тоолуур тус бүр нэгээр буурч байгааг шалгасан боловч тоолуурын анхны зөрүү хэвээр үлдсэн. Урт текст, зөвхөн зайнаас бүрдсэн утга, хайлтын том жижиг үсгийн ялгаа болон буруу бүтэцтэй JSON-ийг энэ session-ээр шалгаж амжаагүй тул дараагийн session-д турших шаардлагатай. Playwright автомат тестээр хоосон талбар, буруу он, давхардсан ном болон устгалын дараах мөр, тоолуурын өөрчлөлтийг assertion ашиглан шалгаж болно. BUG-06-г API түвшний автомат тестээр илрүүлэх боломжтой бөгөөд зөвхөн UI шалгадаг тестээр илрүүлэх нь баталгаатай биш. Харин устгах товчны өнгө, хүснэгтийн байрлал болон урт текстээс үүсэх харагдах байдлын асуудлыг хүний нүдээр шалгах эсвэл visual regression тест ашиглан илрүүлж болно.

## Хэсэг F: AI ашигласан туршилтын дүгнэлт

Лабораторийн ажлын нэмэлт даалгаврын хүрээнд би AI туслах ашиглан exploratory testing-ийн charter-ууд санал болгуулж, өөрийн түүхий тэмдэглэлээр bug report боловсруулуулсан. AI-ийн санал болгосон charter-ууд миний session-д төвлөрсөн ном нэмэх, хайх, устгах болон API-ийн хоосон гарчгийн шалгалтаас гадна статистикийн нийцэл (CH-04), тусгай тэмдэгт ба XSS-ийн боловсруулалт (CH-05), API-ийн алдаа боловсруулах чадвар (CH-06), хэрэглэгчид харагдах мэдэгдлийн нийцэл (CH-07) зэрэг нэмэлт чиглэлийг хамарсан. Миний session-ээр эдгээр бүх чиглэлийг бүрэн шалгаагүй тул урт текст, зөвхөн зайнаас бүрдсэн утга, буруу бүтэцтэй JSON болон байхгүй ID-тай устгах хүсэлт зэрэг нөхцөлийг дараагийн session-д турших боломжтой гэж үзсэн. Мөн T09 болон T10-ийн түүхий тэмдэглэлээ Claude AI-д өгч, хоёр тестийн үр дүнг нэгтгэсэн тайлан болон BUG-06-ийн дэлгэрэнгүй тайлан гаргуулсан. Claude-ийн тайлан T09-ийн хүснэгтийн мөрийн тоо 10-аас 9, нийт номын тоо 11-ээс 10 болсон үр дүн болон T10-ийн `201 Created` статус, `{"result":"OK","id":11}` хариуг миний session report-той нийцүүлэн тусгасан. Гэхдээ AI-ийн тайланд санал болгосон зөвхөн хоосон зайтай гарчиг, `title` талбар байхгүй эсвэл `null` утгатай хүсэлт зэрэг нь миний session-ээр гүйцэтгэсэн тест биш, дахин тестлэх нэмэлт нөхцөлүүд юм. Иймээс эдгээрийг бодит ажиглалт эсвэл батлагдсан согог гэж тооцоогүй. Энэ туршилтаас AI нь тестийн хамрах хүрээг өргөжүүлэх санаа гаргах, түүхий тэмдэглэлийг бүтэцтэй тайлан болгоход тусалдаг боловч үүсгэсэн тайлан дахь үр дүн, утга, тестийн дугаар болон нотолгоог анхны тэмдэглэлтэй тулган шалгах шаардлагатайг ойлгосон.
